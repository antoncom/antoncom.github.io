Stage 1 · 2020–2021 · concept

FAD: every module from one universal block

Working on firmware for network monitoring devices, I noticed that every new feature meant another hand-written service and another hand-made web page. I proposed a different approach and presented it to the client as an interactive prototype of my own — there was no specification behind it.

FAD stands for Functionality – Adapter – Driver. Drivers talk to hardware and protocols (SNMP, HTTP, GPIO), adapters normalise their data, functionalities implement what the user cares about (relays, notifications, logs), and UI widgets display them. All four layers are built from the same block:

Stage 2 · prototype

Resource templates: everything is a resource

The next prototype applied FAD to the user interface. Sensors, output lines, triggers and notifications all become resources created from templates. A template declares which variables it needs — IP address, SNMP OID, polling interval, 1-Wire address — and one variable can be shared by many templates.

The payoff: adding support for a new sensor becomes a matter of describing a template, not writing a new page. The prototype covered SNMP, SNMP traps, webhooks, HTTP relay boards and 1-Wire sensors, plus a template editor that controls which fields the end user sees and in what order.

Stage 3 · prototype

Logic rules: behaviour as ordered, testable steps

Once data is uniform, behaviour can be described the same way. A rule group is a device scenario — say, climate control of a server room — made of ordered rules. Each rule runs a command (set a variable, switch a relay, send a notification) under conditions built from variables tied to sensors and events.

Two ideas from this prototype turned out to matter most in production: a test run that walks through the rules step by step and shows exactly where a scenario breaks, and an event log that records every variable change in plain language.

Stage 4 · production

A rule engine in serial LTE router firmware

The concept was first applied in firmware for a US client’s device controller, and today it runs as the rule engine of the OpenWrt firmware I develop with my team for industrial 4G/LTE routers. Firmware services only report the state of their hardware over the system bus (ubus); every decision — when to switch the SIM card, what to show on the LED, whom to send an SMS, how to react to a GPIO alarm — is made by rules.

  • Rules are small Lua files built from reusable steps, so device behaviour changes without a new firmware release.
  • Field engineers can adjust or add rules themselves, without touching the services.
  • Built-in debugging shows every rule’s values on each pass — the direct descendant of the prototype’s test run.
  • A human-readable event journal on the device continues the prototype’s event log.
The production engine is proprietary to my current employer, so this page shows only the prototypes I authored and describes the engine at the level of ideas. I am glad to walk through the design in an interview.
